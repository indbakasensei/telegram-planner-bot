# BAKA v15.0 — Workspace OS (Architecture Milestone)

**Status:** Design & planning only. No production code. These documents
define how BAKA evolves from a Telegram productivity bot into a
**Personal Workspace Operating System** while preserving 100% of
existing functionality.

## The seven load-bearing decisions

Every document below flows from these. They exist to make **"no
regression"** a structural property, not a promise — by reusing the
exact v14 playbook that already shipped six domains safely.

1. **Additive layer, ships dark behind a flag.** Workspace is a *new*
   `core/workspace/` package + *new* tables + *nullable* FKs on the
   existing tables, gated by a `WORKSPACE` feature flag (default OFF).
   When OFF, every current code path is byte-identical — exactly how the
   Offline Engine (v14.2–14.11) shipped complete while dark.
2. **Everything belongs to a Workspace; the default is `Inbox`.** The
   abstraction is universal without forcing anyone to organize: loose
   tasks/habits/memories land in a per-user Inbox workspace, so
   migration changes nothing visible.
3. **Composition over inheritance for Templates.** A Template is a
   registered *config* (sections, default milestones, views, icon), not
   a subclass. Same engine, different template — literally the milestone's
   core principle. Registration-based, like the Offline `ActionRegistry`
   (ADR-012) and the v14.22/14.23 self-test / regression registries.
4. **The Timeline is append-only (event-sourcing-lite).** Immutable
   events, auto-generated by hooking write operations. The SQLite tables
   remain the authoritative state; the timeline is a derived,
   human-readable audit/journal with retention + full-text search.
5. **Telegram is a projection & archive, never the source of truth.**
   SQLite is authoritative. A durable *outbox* + a sync worker posts
   events to Topics; tolerant of Telegram downtime (queued, retried,
   idempotent). This is the notification_service reliability pattern
   (v13.0) applied to workspace sync.
6. **The AI Orchestrator is a new layer ABOVE the existing stack.** It
   adds workspace-awareness (active-workspace resolution, entity
   resolution, action planning, safety rules) on top of the current
   Intent Engine / Routing / Offline Engine / `baka_brain` — it does not
   replace them.
7. **Migration = backfill, never move.** Add columns, create Inbox,
   convert existing Projects to Workspaces, backfill `workspace_id`. Old
   tables, commands, and the 44-test regression suite keep passing —
   which is the proof of no regression. Reversible: flag off restores
   today's behaviour.

## What preservation means concretely

The v14 **Definition of Done** and the **Quick Release Suite** (44
manual tests, `core/regression`) are the acceptance gate: v15 is not
"done" until every existing regression test still passes with the flag
both OFF and ON. Tasks, Habits, Reminders, Projects, Memory, AI
commands, the database, and the automated pytest suite are constraints,
not negotiables.

## Reused v14 foundations (nothing is invented from scratch)

| v15 need | Existing pattern reused |
|---|---|
| Ship dark, enable later | Feature flags (`core/feature_flags.py`, v14.1C) |
| New domain package | `core/offline/`, `core/selftest/`, `core/regression/` structure |
| Registration-based dispatch | `ActionRegistry` (ADR-012), selftest/regression registries |
| DB access without raw SQL sprawl | Storage Facade (`core/storage/`, v14.1C) |
| Reliable outbound delivery | `notification_service` rate-limit + retry (v13.0) |
| Additive, idempotent schema | `init_db()` ALTER-in-try/except pattern |
| AI layered above deterministic core | Intent Engine → Routing → Offline → Legacy (v14) |
| Immutable decision logging | Offline `[Offline]` / timeline events, `interaction_log` |
